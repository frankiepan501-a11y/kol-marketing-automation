# 经验记录

- 公开聚合页只解决“邮箱来源证据”问题，不等于邮箱一定有效；仍必须经过严格邮箱验证。
- 搜索结果摘要、平台内部跳转链接和同名社交账号不能作为官网或邮箱的写回证据。
- 生产主表补数据必须是“只补空值 + 写前重读 + 写后回读”，否则并发时容易覆盖运营刚补的数据。
- 已有邮箱字段只要存在任何原始内容就不能覆盖，即使旧值格式异常；旧数据修复要走独立审计流程。
- YouTube 外链必须只解析官方 `channelExternalLinkViewModel` 数据，不能扫描页面 JSON 里的所有 `url`，否则会把系统接口或内部资源误认成官网。
- 飞书大表在较高并发下可能返回 `1254607`；生产补数应低并发、失败关闭，不能边读失败边继续写。
- 对空邮箱难样本，单条 `get_record` 即使并发仅 3，50 条批次仍可能因飞书 `1254607` 出现 1-2 条读取失败；降低并发不是永久修复。邮箱只读检查应使用稳定 list API 一次批量读入后本地处理，正式写入前再保留单条重读与写后回读。
- 批量读取修复后必须按 10→30→50 逐级复测，而不是直接宣布可全量；本次三档均零写入、无处理错误，证明修复覆盖了原故障点，但不代表已经获得正式回填授权。
- 直接运行生产试跑脚本时，如果当前进程没有加载生产配置，会安全失败但不能得到有效业务结论；后续必须使用只注入允许变量的 Zeabur 安全包装脚本，并确保输出不打印凭据。
- 稳定批量快照适合只读检查，但不能自动等同于正式写入时的最新事实。耗时的页面抓取和邮箱验真结束后，必须刷新跨记录唯一性索引；逐条写前还要核对产生结论所依赖的来源字段，而不只是目标写入字段。
- “前置资料不足”和“外部服务故障”必须使用不同业务状态。两者合并后，团队会错误地重启服务、改凭据或重跑全批；正确做法是把无公开邮箱、姓名不足、授权错误、HTTP 错误、网络错误和超时分别统计，同时保持同一严格写入门槛。
