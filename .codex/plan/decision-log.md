# Decision Log

## 2026-08-20 食人花自治补池 P0

- 采用现有 Zeabur 服务 + n8n 定时器，不创建依赖本地 Codex 会话的重复自动化；这是24小时生产链路，且已有唯一发送中心和运行锁。
- `success` 只用于业务结果也可接受的运行；当剩余额度>0、动作=expand、库存=0且本轮补给无进展时，标记为 `degraded`，由独立审计捕获。
- 自治补池继续只产生候选、参与记录和草稿；真实邮件仍只由现有10分钟发送中心发出。
- 不用放宽筛选标准换取数量；机器能确定的合格对象自动入队，资料不足和语义边界对象进入运营审核并附结构化原因。
- 定时审计只消费服务端`business_outcome`合同，不在n8n复制另一套补池判断；合同字段缺失或枚举非法时按失败处理，防旧版本/损坏返回假成功。
- 供给进展不再把参与记录、草稿、爬虫任务等不同单位相加成一个含糊总数；对外返回`made_supply_progress`和`supply_progress_breakdown`分项。
- 本次动态拓词严格限定食人花活动，Dave不启用AI扩词。
- 活动爬虫任务只在创建后2小时内视为有效在途供给；超时任务不再令任务维持假成功，系统会尝试补新词，仍无供给则明确`supply_blocked`。
- 定时审计必须保持单例：脚本更新现有工作流，不重复新建；迁移期发现新旧两条时自动停用旧版。
- 当前生产是Zeabur单实例；部署重启会终止旧后台协程，因此跨重启残留的`running`不能作为活任务租约。并发去重只认当前实例内存任务，持久记录继续用于审计和结果回读。
- 同一条审计包含Dave和食人花两条分支时，Dave在合理运行窗口内不得先报错阻断食人花分支；两条任务的运行中窗口与完成态均需分别验证。

## 2026-08-21 全链路只读审计

- “今天发了多少封”统一按活动参与记录关联的真实已发送草稿和北京时间发送日期统计，不用品牌邮箱滚动24小时总量代替；品牌邮箱总量会混入回复、寄样、报价和其他任务。
- n8n定时任务是否正确必须同时满足：业务名称、显式timezone、cron表达式、真实execution北京时间四项一致；`active=true`和名称里的“BJ”都不是执行正确的证明。
- 当前集中宣发模式不再把“能自动补池、能发信”视为完整闭环；必须能从回复/洽谈回填承诺、从上稿登记回填实际结果，控制器才有可靠停止线。
- 补池业务进展不能只看“写了多少条资料”；若新增候选、待审核对象、发现任务和草稿均为0、库存仍为0，连续资料刷新不得长期维持`supply_in_progress`。
- 本次只审计并登记待办。所有生产定时修正、活动结果回填和运营卡片建设须另行实施并验证。

## 2026-08-21 KOL集中宣发任务日报卡

- 卡片主标题固定为`KOL集中宣发任务日报 · YYYY-MM-DD`。KOL/P2使用Card JSON 2.0头部彩色标签表达，不把统一通知前缀写入主标题。
- 为避免影响既有通知，`send_card_message`只新增默认开启的标题格式开关；日报显式关闭，其他调用方行为不变。
- 日报只读汇总，不调用补池、事实回填、草稿生成或邮件发送函数；读取失败显示红色数据异常，不用猜测值补齐。
- 活动开发信与Zoho邮箱额度保留两套口径：前者只算活动参与记录关联的真实已发送cold草稿，后者算品牌邮箱滚动24小时全部外发。
- 第一张真实样卡只发Frankie。实际渲染未经确认前，不创建或启用每天17:15发运营群的定时任务。
- 食人花发信修复验证不再设计飞书提醒卡，改为Codex只读回查并在当前任务汇报。
- 后台请求不能用字面量`today`或只按`notify/frankie_only`去重；必须先解析北京时间日期，并把明确收件人和当前执行中活动ID集合纳入请求键，防跨天复用旧日报或活动集合变化后漏算。
- 日报汇总仍保持业务只读。为防Zeabur重启后重复发卡，只有`notify=true`允许在一个活动的`数据口径备注`记录发送中/已发送技术回执；同时使用飞书确定性`uuid`和写后回读。技术回执写入单独计数，不能冒充“完全无写入”。
- Card JSON 2.0正文说明只用`markdown`等受支持组件，不使用旧`note`。只有发送接口真实状态前缀为HTTP 400且包含`Failed to create card content`，才能证明消息创建前失败并把回执标为`rejected`；5xx、超时和空message_id均不得自动重试。
- Frankie-only真实样卡已发送成功，但每天17:15运营群定时发送继续保持未启用；必须等Frankie确认真实客户端里的颜色、进度条和排版后再开。
- Frankie已确认紧凑版真实前端排版通过。生产改为独立的17:15日报工作流，不改现有17:00反馈控制；定时器显式使用`Asia/Shanghai`，先异步启动日报，再等待12分钟回读任务状态，只有结构校验通过、确实群发1张、未发生业务写入时才把n8n execution判为成功。
- 生产群发继续使用聪哥分身1号，目标只允许当前KOL运营群`oc_8b71a652a25ec0dd1c8af2c53e86ed93`；旧站外运营群不作为降级目标。首次真实群发后的客户端视觉验收仍单列，不用工作流`success`替代截图检查。

## 2026-08-21 三项P0连续实施

- 食人花动态拓词保留DeepSeek作为首选，但外部模型欠费/不可用不得令补池停摆；仅食人花活动增加受控确定性降级词库，范围限制为Nintendo/Mario收藏、游戏房、主机硬件评测，不放宽国家/语言/重复触达和人工审核规则。
- 降级词库只有实际创建发现任务才算供给进展；资料刷新仍只作为观察数据，不能让任务从`degraded`变回成功。
- 旧n8n工作流过去按UTC换算cron，但实例实际按上海时区解释；本次两条高风险流统一显式写`Asia/Shanghai`并直接使用业务当地时间，避免名称、cron和实际执行再次漂移。首次真实execution验收单独留到下一个周一，不用配置回读替代业务产物回读。
- 活动承诺只接受“明确发布动作与具体日期出现在同一句/同一分句”的回复事实；报价、兴趣、泛洽谈、引用的活动窗口均不计承诺。宁可暂时少计，也不允许控制器因假承诺提前停止扩池。
- “预计按时上稿”只从`实际上稿时间`计算，不再从`承诺上稿时间`推算。上稿链接只接受该活动关联草稿里的内容级`live_link_received`证据；实际时间还必须有同回复“已发布+具体日期”。KOL主表是跨品牌全局字段，无论当前有几个活动都不自动归因。
- 邮件事实写入前必须同时满足三层隔离：英/德/西语引用历史已剥离、参与记录活动ID精确相等、事实来源草稿唯一归属当前参与记录；任一失败都不写。
- 活动事实回填错误不是普通统计误差：控制器必须改为`hold`，后台任务标`degraded/outcome_reconcile_failed`并告警，不能继续按旧承诺/上稿数据自动扩池。

- 同一次灰度只允许一个可识别批次。重复提交不能通过换未使用词继续建下一批，必须先完成本批“发现→有效邮箱→合格/待审→排除原因”验收。
