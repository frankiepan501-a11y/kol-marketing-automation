# Decision Log

- 归类为公司改造 L3“交接界面”：系统先做确定性判断，只把活动归属边界交给运营；Frankie 审系统，不逐条审 KOL。
- 不把“从统计排除”当作完成；可继续推进的回复必须有明确下一节点。
- 默认不新增表/机器人；优先复用既有草稿表、参与者表和 event-hub 回调。若现有字段无法安全持久化，再提出最小 schema 变更。
- 草稿表只新增归属 ID、状态、确认人、确认时间和卡片消息 ID 五个字段；不改邮件状态、不直接发送邮件。
- 卡片仍由聪哥分身3号发送和 PATCH；事件中心只认精确 action，避免新分支吞掉其他卡片。
- 生产自动扫描开关默认关闭；先发 Frankie-only 样卡并完成真实回调验证，再显式开启运营路由。
- 定向扫描的内部诊断元数据不得通过 `**kwargs` 穿透到业务函数；边界处使用参数白名单，诊断字段只出现在 API 结果与日志中。
- 当前食人花只有 1 条未归属回复。它的原回复审核卡已经送达，因此归属确认后继续使用原卡，不重复发回复卡；只需补写活动归属并恢复日报统计。
- 入站 `回复原文` 与出站 `邮件正文` 是不同业务事实，展示层禁止互相兜底。历史入站正文缺失时必须明确显示缺失，并把系统草稿放在独立、无歧义的区域。
- 已发送样卡的字段纠错优先 PATCH 原卡，不新发一张；这样运营只面对一个待处理入口，也避免重复点击和重复归属。
- 原卡刷新是单条纠错动作：必须带 `reply_record_id`；若记录没有旧卡 message_id，系统只返回缺口，不得降级为新发卡。
- 真实点击验收通过只证明“卡片—回调—写回—原卡结果态”闭环可用，不自动授权开启批量扫描。`LAUNCH_REPLY_ATTRIBUTION_ENABLED` 必须作为单独的生产授权闸。
- 活动归属卡解决“这封回复属于哪个活动”，原回复审核卡解决“运营该如何回复和推进”；两者不能合并，也不能把归属确认误当成回复已处理。
- 已证实只有一条食人花存量未归属回复且已完成修复，因此删除“批量灰度修复存量”的过期待办。后续未归属回复只处理新自然流量。
- 项目收口以自然日报与多维表格事实一致为准；业务候选供给不足、运营待处理回复和固定日期测试债务分别管理，不再重新包装成技术 P0。
