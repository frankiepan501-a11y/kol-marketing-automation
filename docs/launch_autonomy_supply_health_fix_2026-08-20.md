# 食人花自治补池业务健康 P0 修复（2026-08-20）

## 结论

原自治任务只判断“代码有没有报错”，没有判断“补池有没有产出”。因此出现 POWKONG 仍有大量滚动24小时额度、食人花可发库存为0，但后台任务和n8n审计都显示成功的假健康状态。

本次把完成标准改为业务结果，并让食人花补池和独立审计都改为15分钟周期。真实邮件仍只由既有10分钟发送中心发出。

## 根因

1. `app/main.py` 在 `autonomous_refill` 正常返回后固定写 `status=success`。
2. 持久状态只保存额度和库存，没有保存补池是否产生画像刷新、候选、发现任务或草稿。
3. 活动专用确定性关键词用完后，`ensure_campaign_supply` 会返回创建0条，但不会继续生成新的定向发现词。
4. n8n完成审计只检查状态和更新时间，没有检查“剩余额度>0、库存=0、补池进展=0”。

## 修复

- 增加业务结果：`ready_inventory_created / supply_in_progress / supply_blocked / inventory_sufficient / quota_exhausted / held / stopped`。
- “动作仍为expand＋剩余额度>0＋库存0＋补池0进展”写为 `degraded`，不再冒充成功。
- 持久状态增加 `business_outcome`、`made_supply_progress` 和分项计数
  `supply_progress_breakdown`，只保留安全计数，不保存KOL个人信息。
- 已创建或两小时内仍在待触发/执行中的活动爬虫任务记为供给进行中；超过两小时的任务记为过期，不再掩盖补池阻塞，并允许系统补新的未使用关键词。
- 暂停、窗口结束、库存充足、额度用尽等提前返回也统一输出完整业务合同，定时验证不会把正常停止误判为字段损坏。
- 结构化审核原因码直接在筛选判断点生成；展示文案变化不会让原因码静默丢失。
- n8n 更新脚本必须复用现有审计工作流；若历史名称与新名称并存，只保留新业务审计启用，旧小时审计自动停用，避免重复检查。
- Zeabur部署重启后，旧进程的后台任务已经终止；活动表里残留的`running`只用于回读，不再阻止新实例立即重开补池。当前生产保持单实例，真实并发仍由进程内活动锁和任务表阻止。
- 活动固定关键词耗尽时，自动生成新的主题定向搜索词；后续仍经过国家、语言、内容、活跃度、历史关系和重复触达硬筛，未降低质量标准。
- 待补资料对象写入结构化 `审核原因代码`，运营可以直接按原因筛选，不再面对空原因记录。
- 食人花启动频率改为北京时间每小时05/20/35/50分；业务审计改为12/27/42/57分。运行中任务在45分钟合理窗口内不误报，完成任务必须通过业务结果检查。
