## 数据与执行流程

1. n8n 每日只触发一个 NYXI 专用服务请求，必须指定配置行 `recvrM7WDZ0ZV9`，不能调用省略品牌的 `/run`。服务持有单运行锁，防重叠。所有后台步骤返回独立 job_id，定时器只能在最终状态为完成时认定成功，不能把 HTTP 202 当完成。
2. NYXI 的 `search.list` 从上次成功水位往前重叠 48 小时到本次运行时间。新 ID 用 `YouTube + video_id` 去重入竞品帖子库。成功写完帖子才推进 NYXI 水位；失败保持原水位。当天尚无水位时沿用既有安全起点，不做多年历史重扫。
3. 每日仅刷新发布日期在运行时刻前 30 天内的已入库 NYXI 视频的公开播放等数字，再加本轮新发现 ID。更老视频每周一在日常增量完成后按稳定帖子 ID 排序；设旧帖数为 N，批次数 `ceil(N/100)`，批号为自 2026-09-21 起的周数对批次数取模，只刷新 `[批号×100, min((批号+1)×100,N))`。每次报告批号、选中和完成数；失败不改 NYXI 增量水位，下周轮转最终会再次覆盖该批。不能让日任务重扫 2,400 多条历史记录。刷新失败不得报告为零更新。
4. 新账号按稳定 YouTube channel ID 去重；排除已核验的两个 NYXI 官方频道 `UCIY4yC2qUCPcM7ws-xTARYg`、`UCbvp-CTcH3Mhtj2UWsSy8sA`。日报的“新增”以本业务日期第一次尝试前的已成功水位为基线，合并本日所有尝试的 `batch_id` 与帖子 ID 后去重；部分写入失败后重跑，先前已落库的帖子仍计入该日结果，不按“本次重跑前的库”重新置零。链接指向这些视频与非官方候选频道。不能仅凭关键词命中就宣称已签约；误命中或待分析帖要标为候选。日报包含新增帖子数、非官方新账号候选数、链接、刷新数、失败状态及本次 NYXI search 调用数。无新增时也明确写“采集成功，新增 0”。
5. NYXI 完成后读 Google Cloud 中使用该 `YOUTUBE_API_KEY` 的同一项目当天 `search.list` 专用配额的上限与实际已用量；读数必须标明项目 ID、指标/单位、对应太平洋时间日期、采样时间。启用 8BitDo 的前置验收是：由有权查看该 API key 的 Google Cloud 项目确认 key→project 映射；从该项目 Quotas 页面确定 `Search Queries per day` 的实际 metric/limit 标识；再用对应 Google Cloud 只读配额接口取得该标识的限额和用量，并与页面同一时刻数值核对。当前尚未找到可用的 Google Cloud 配额只读凭据，也未完成这个指标映射与接口 smoke；在完成前 8BitDo 自动补采始终为关闭。只接受距检查时刻不超过 5 分钟、且采样时间晚于 NYXI 最后一页搜索的读数；否则 `quota_unknown`，8BitDo 不执行。读数与本地调用计数不等价，其他程序可能共享项目；运行中每个补采小段前重读，并预留至少 20 次搜索给外部调用及下一次 NYXI。官方 2026-09-15 更新的配额页明确：`search.list` 是独立的每日搜索桶，默认 100 次，每请求（包括翻页）扣 1 次；其它端点共用另一 10,000 单位桶。实际项目数值以同口径读数为准；若 Google 指标口径变化或无法读到这个搜索桶，不以旧单位公式猜算。
6. 仅当 NYXI 已完成且搜索桶 `remaining >= 10 + safety_reserve`，允许 8BitDo 从现有 `YouTube历史游标` 进入最多一个 7 天窗口。窗口拆为“一个查询词 × 一个 UTC 日期”的小段，每小段最多 10 页，最坏消耗 10 次搜索；每小段开始前重新取得第 5 条合格读数。第 10 页仍返回 `nextPageToken` 时该小段是 `overflow`，不能标完成：先将它按 UTC 时间一分为二并分别跑；继续溢出则递归拆到 1 小时，1 小时仍溢出就保留未完成状态并停止、报告人工处理。小段内结果先按 `YouTube + video_id` 幂等写入，无下一页且完整写入后才在既有 `YouTube历史游标` JSON 中记录已完成的时间段/查询词；中断时重跑未完成小段第一页，不持久化易失效的 pageToken，已写页靠唯一键去重。只有所有叶子时间段与查询词均完成才推进主 `next_end` 到 7 天窗口起点并清除细分断点。预算不足、读数过期或 Google 配额错误时停止，保留断点和主游标；日报区分暂停、失败、完成。单个小段失败可能重用最多 10 次查询额度，但不会漏采或提前推进主游标。
7. 全部采集或安全暂停结果已知后发送一条日报，包含“8BitDo 补采已完成 / 因额度暂停 / 因 NYXI 失败未启动”及下一游标。现有关键词配置表新增一个文本字段 `YouTube日报回执JSON`，以“北京时间业务日期 + NYXI日报”作唯一业务键存状态、消息 ID、发送时间和本日首个尝试的水位。先把该业务键写成 `sending`，回读成功后才调用飞书发送；收到成功响应后写 `sent` 与 message_id。若发送超时、回执写入失败或进程崩溃，保留 `sending`，自动重试不得再次发送；先在指定群按业务键查当天消息，找到则补记回执，查不到但结果不确定则转人工核验，不静默补发。已有 `sent` 的正常重试不再发送。同日主动重跑若需更新结论，必须明确标“更正”并引用原消息，不伪装成第二条日常日报。若群发失败，记录明确错误并让任务显示失败，不得静默改用旧机器人。服务层异常不得被 n8n 的 HTTP 成功状态掩盖。

## 组件边界

- 采集器：负责 NYXI 搜索、近 30 天数字刷新、8BitDo 单窗口补采以及帖子/游标写入。输入是现有关键词配置和运行时间；输出是有状态与计数的结果。它不发消息，也不写 KOL 主表。
- 配额闸：只读获取 Google 项目配额快照、计算安全余量、提供每个补采小段开始前的预算决策。输入含项目身份、当天日期、已用/上限与估算；输出是允许/暂停及原因。读取失败时默认暂停。
- 日报器：使用服务现有 KOL媒体助手飞书凭据，向唯一指定群发送结构化文本；只消费采集结果，不发卡片、不触发回调，也不迁移其它通知。
- n8n：只定时启动、轮询最终状态和暴露失败，不直接决定配额，也不并行启动两个品牌。

## 验收与上线

先用模拟 YouTube/飞书/Google 读数测试：NYXI 成功且余量足、NYXI 失败、配额未知、配额不足、窗口中途耗尽、重复执行、消息发出后回执写入失败或发送结果未知、官方频道排除、零新增、旧帖不日刷。再在云端以 preview 核对配置和数量，部署现有服务并回读版本与身份；先向目标群发一条明确标注“测试”的消息，回读 message_id。随后修改现有 n8n 工作流，保留原凭据引用和其它节点配置，回读 active 与每日 cron。首次真实运行只按当天顺序验收，不补发旧日报；核对帖子唯一键、NYXI 水位、8BitDo 游标、群消息和 job 状态。未取得可信 Google 项目配额读数前，可上线 NYXI 每日与日报，但 8BitDo 自动补采必须保持关闭，日报必须明示“配额不可验证，补采暂停”。

回滚：停用现有 n8n 工作流或恢复其完整旧定义；服务回到已验证版本 `d52e2bb`。回滚不得删除帖子或重置历史游标。失败必须留下 job_id、原因和单条可回放线索。
