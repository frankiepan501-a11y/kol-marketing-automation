# KOL 活动竞品证据与参与记录设计

状态：已获 Frankie 口头确认，独立规格复核修订中

日期：2026-08-19

## 1. 目标

在现有“日常持续开发”与“定点集中上稿”双模式基础上，补齐两项能力：

1. 运营创建集中宣发活动时，明确选择以下一种竞品证据模式：
   - 发起新的竞品分析并引用；
   - 引用已有竞品证据；
   - 不使用竞品证据。
2. 用独立的“活动参与记录”保存一位 KOL 或媒体人在一次活动中的入围依据、执行进度和结果，不覆盖联系人主状态。

首个试点仅把现有 NYXI 证据接入 FUNLAB YS11-5 潜水员戴夫联名款的 2026-09-15 集中发布活动排序。食人花活动、日常派单和其他产品不受影响。

## 2. 业务原则

- 竞品证据是可选增强项，不是创建 KOL 活动的必备条件。
- 任务创建时必须明确选择证据模式，但“选择不使用”是完整、合法的路径。
- 竞品公开曝光和合作信号只用于活动候选优先级，不代表我方合作关系、订单、销售额或 ROAS。
- 联系人身份、全局重复触达预检、邮件发送限额、回复线程、寄样、SLA 和上稿登记继续复用现有系统。
- 活动状态不写回 KOL/媒体人主表，不批量复制 NYXI 摘要到联系人字段。
- 证据未准备好时允许活动准备和候选基础预览继续，但禁止锁定最终名单和真实发信。

## 3. 范围

### 本期包含

- 为活动主表增加竞品证据选择、证据状态、证据引用和名单锁定控制字段。
- 新建一张“新品集中上稿活动参与记录”表。
- 扩展活动候选预览，使其接受 `campaign_id`，按活动证据模式决定是否应用竞品排序。
- 只为戴夫试点活动绑定已有 NYXI 证据。
- 保持候选预览、单条回放和排序验证为只读；不产生真实 KOL 邮件。

### 本期不包含

- 不要求每个活动都发起竞品调查。
- 不改现有日常 `score_kol` 和媒体人评分。
- 不把竞品分数或活动阶段写进 KOL/媒体人主表。
- 不新建通用“证据包”表；复用现有“竞品帖子监控库”和“竞品新品与营销事件”。
- 不自动把无法稳定匹配的竞品作者新建为 KOL。
- 不对真实 KOL/媒体人发送邮件、产生费用或寄样。
- 不在本期实现竞品研究采集器的新平台或新算法。

## 4. 现状与设计选择

KOL 营销管理库当前有 27 张表。活动主表有 36 个字段，但没有竞品证据模式；活动节点表有 13 个字段，但没有活动参与明细。现有竞品数据已经集中在：

- `tblCDbvLtnLzdxEp` 竞品帖子监控库；
- `tblpZaWYEWy54Sll` 竞品新品与营销事件；
- `tblgWfvdPgbkq541` 竞品关键词监控配置。

采用“活动主表 + 活动参与记录 + 复用竞品证据表”。不采用把竞品分写入 KOL 主表的方案，也不在本期增加证据包、决策日志等额外表。

## 5. 组件边界

### 5.1 活动主表

负责保存一次活动的目标、时间、预算、竞品证据选择和外部动作授权。它回答“本次活动采用什么规则”，不保存每位 KOL 的执行进度。

### 5.2 竞品证据表

继续保存公开帖子和营销事件。活动排序的唯一权威范围是活动字段 `关联竞品帖子`；营销事件只提供产品发布时间和节奏背景，不得扩大或缩小帖子范围。不复制完整帖子正文和整套运营指标；允许在参与记录的 `排序快照历史` 中保存完成决策审计所必需的精简不可变指标快照。

### 5.3 候选预览与单条回放

负责读取活动、产品、联系人、历史草稿和竞品证据，返回候选排序及理由。该组件只读，不创建任务、草稿、参与记录或邮件。

### 5.4 活动参与记录

负责保存进入活动名单的对象及其活动内生命周期。只有通过资格检查并入围或同线程激活的对象才落表；基础预览中的全部候选不落表。本期不支持人工绕过资格检查加入。

### 5.5 现有执行流水线

名单锁定并获得发送授权后，继续复用现有任务、草稿、Zoho 限速、回复、寄样、SLA 和上稿登记流程。新功能不建立第二套邮件发送器。

## 7. 活动参与记录表

新表名称：`新品集中上稿活动参与记录`

一行代表“一位 KOL 或媒体人 × 一次活动 × 一个产品家族”。一个活动当前只绑定一个产品主记录，但唯一键仍保留产品家族维度，避免未来扩展为多产品活动时冲突。

唯一键格式：

```text
campaign_id|product_family_id|object_type|contact_record_id
```

### 7.1 身份与来源

| 字段 | 类型 |
|---|---|
| 参与记录ID | 文本，主键 |
| 活动ID | 文本 |
| 关联活动 | 关联活动主表 |
| 对象类型 | 单选：`KOL` / `媒体人` |
| 关联KOL | 关联海外KOL主表 |
| 关联媒体人 | 关联海外媒体人主表 |
| 产品家族ID | 文本，使用活动主记录ID |
| 进入方式 | 单选：`新开发` / `同线程激活` / `继续洽谈`；本期不允许人工绕过资格检查加入 |

### 7.2 排序依据

| 字段 | 类型 |
|---|---|
| 基础评分快照 | 数字 |
| 竞品证据等级 | 单选：`A` / `B` / `C` / `无加分` / `待人工匹配` |
| 关联竞品帖子 | 多条关联竞品帖子监控库 |
| 最终优先级 | 数字 |
| 选择原因 | 文本，保存人能读懂的排序理由 |
| 排序版本 | 文本，与活动证据排序版本一致 |
| 排序快照历史 | 多行文本，由服务追加不可变 JSON 条目，保存第 10 节定义的完整解释快照 |

### 7.3 执行进度

| 字段 | 类型 |
|---|---|
| 参与状态 | 单选，见第 8 节 |
| 锁定批次ID | 文本，用于批量写入失败时定位同一批记录 |
| 名单版本 | 文本；只有等于活动 `已锁定名单版本` 的记录属于当前名单 |
| 取消原因代码 | 单选：`锁定失败` / `运营取消` / `不再符合`；只有锁定失败允许系统自动重试 |
| 关联KOL任务 | 关联 KOL 营销任务台 |
| 关联媒体人任务 | 关联媒体人营销任务台 |
| 关联邮件草稿 | 关联邮件草稿表 |
| 计划上稿时间 | 日期时间 |
| 承诺上稿时间 | 日期时间 |

### 7.4 本期结果边界

本期不在参与记录表新增曝光、订单、销售额和成本字段。这些指标需要另行确认数据来源、归因窗口、币种、退款与样品/物流成本口径，不能先建出含义不清的字段。

本期只预留以下结果字段，不提供写入接口，也不自动同步。上稿登记、曝光和销售归因在后续独立规格中接入。

| 字段 | 类型 |
|---|---|
| 实际上稿时间 | 日期时间 |
| 上稿链接 | URL |

### 7.5 身份与并发约束

- `对象类型=KOL` 时必须且只能填写 `关联KOL`；`关联媒体人` 必须为空。
- `对象类型=媒体人` 时必须且只能填写 `关联媒体人`；`关联KOL` 必须为空。
- 所有参与记录只允许通过一个活动服务入口写入；当前 Zeabur 服务保持单实例。
- 服务按 `campaign_id + product_family_id` 获取进程内互斥锁，再搜索唯一键、创建或返回原记录。
- 创建后立即再次查询唯一键；若发现多行，停止本批次、把活动标记为阻塞并要求人工处理，不创建任务或草稿。
- 在服务扩为多实例前，必须先增加跨实例锁或具备唯一约束的幂等存储；本规格不允许在现有仅进程锁的情况下直接横向扩容。

## 8. 参与状态

候选只存在于只读预览中，不落参与记录表。名单锁定成功后才创建参与记录，初始状态为 `已入围`。

未来正常路径：

```text
已入围 → 已批准触达 → 已发信 → 已回复 → 洽谈中
→ 已承诺 → 已寄样 → 已上稿 → 已完成
```

异常终态：

```text
已排除 / 已拒绝 / 无回应 / 寄样未产出 / 已取消
```

参与状态只描述这次活动。它不能覆盖联系人主表中的长期合作状态。

本期只允许服务写入 `锁定准备中`、`已入围`、`已取消`。`已批准触达`及其后的状态属于未来外联阶段，本期接口必须拒绝写入。

未来阶段的状态裁决规则如下：

- `已批准触达` 只能由活动名单人工批准动作产生。
- `已发信` 以 Zoho 已发送箱和现有草稿发送状态为准；参与记录不能自行宣称已发信。
- `已回复/洽谈中/已承诺/已寄样` 以现有回复、草稿和寄样记录为准；冲突时现有业务表为事实来源。
- `无回应` 使用现有完成周报口径：末次发信满 14 天且没有回复。
- `寄样未产出` 使用现有完成周报口径：签收满 60 天且没有上稿。
- `已上稿` 表示已保存实际链接和上稿时间；`已完成` 表示活动归因观察期结束并完成结果复盘。
- 异常终态重新进入活动必须由运营明确恢复，服务追加状态变更记录，不静默回退。

## 9. 三种证据模式

### 9.1 发起新分析

1. 活动服务在现有活动节点表创建或复用 `节点代码=competitor_research` 的准备节点，保存竞品品牌、产品关键词和活动 ID；本期不开发新采集器。
2. 现有竞品调查工具、现有采集工作流或人工调查继续把帖子和营销事件写入既有竞品表。节点只负责跟踪请求与状态，不复制证据。
3. 活动服务提供 `POST /launch/campaigns/evidence/start`，把合法状态从 `待分析` 推进到 `分析中`；调用失败时写入节点阻塞说明并将状态置为 `失败`。
4. 调查完成后，执行人通过 `POST /launch/campaigns/evidence/submit` 提交活动 ID、候选帖子 record_id 和可选营销事件 record_id。服务校验帖子属于选定竞品品牌后，把候选 ID、提交说明、提交时间和新配置版本写入 `competitor_research` 节点，并把活动状态从 `分析中` 推进为 `待人工确认`；此时候选仍不参与正式排序。
5. 运营通过 `POST /launch/campaigns/evidence/confirm` 提交活动 ID、最终帖子 record_id 列表、可选营销事件 record_id 列表和 `expected_config_version`。最终列表必须是当前节点待确认集合的子集。服务回读帖子，要求 `人工复核状态=已确认`、`相关性=相关`且竞品品牌一致；事件若提供则要求 `人工确认状态=已确认`。通过后写入活动权威帖子清单、事件背景、证据快照、新配置版本和排序版本，并置为 `已就绪`。
6. `POST /launch/campaigns/evidence/retry` 只允许从 `失败` 回到 `待分析`，并递增配置版本；它不删除旧帖子或事件。
7. 活动节点、状态推进、调查结果提交和人工确认共同构成可执行的新分析路径；采集本身继续复用现有能力。
8. 创建活动后，其他准备和候选基础预览继续。
9. `竞品分析状态` 为 `待分析/分析中/待人工确认` 时：
   - 候选预览可返回基础排序，并显示 `evidence_pending=true`；
   - `名单锁定授权` 必须保持关闭；
   - `发送邮件授权` 即使被误勾，也不能绕过名单锁定门槛。
10. 分析失败时不自动降级为“不使用”。运营必须选择重试、改用历史证据或明确不使用证据。

### 9.2 引用历史证据

1. 运营选择竞品品牌和已经确认的历史帖子；可同时选择一个或多个已确认营销事件作为背景分组。
2. 系统保存选定帖子清单、证据快照时间和排序版本。
3. 候选预览立即使用活动专用证据排序。
4. 证据记录后续更新不会静默改变已锁定名单；需要生成新排序版本并重新确认未发送候选。

### 9.3 不使用竞品证据

1. `竞品分析状态=不适用`。
2. 关联营销事件和关联竞品帖子均为空。
3. 候选按现有基础评分和全局重复触达结果排序。
4. 不产生“缺少竞品证据”告警，不阻塞名单锁定。

### 9.4 合法组合矩阵

| 证据模式 | 竞品品牌 | 关联帖子 | 关联事件 | 合法状态 | 名单可锁定 |
|---|---|---|---|---|---|
| 发起新分析 | 必填 | `已就绪`前可空；`已就绪`时至少1条已确认帖子 | 可空；填写时必须已确认 | `待分析→分析中→待人工确认→已就绪`；任一步可到`失败` | 仅`已就绪`且帖子/事件全部通过校验 |
| 引用历史证据 | 必填 | 至少1条已确认帖子 | 可空；填写时必须已确认 | 只允许`已就绪` | 是 |
| 不使用竞品证据 | 必须为空 | 必须为空 | 必须为空 | 只允许`不适用` | 是 |
| 空或未知旧值 | 不采信 | 不采信 | 不采信 | `配置无效` | 否；只允许基础预览并显示错误 |

服务在预览、确认和名单锁定前都重新验证矩阵：

- `不使用`却保留品牌、帖子或事件时返回配置错误，不自动清理或猜测。
- `引用历史证据`不能处于待分析、分析中、失败或不适用。
- `发起新分析`不能仅人工把状态改为已就绪；必须存在已确认帖子和成功确认动作。
- 关联帖子或事件被删除、驳回或改回待确认后，活动在下次读取时按 fail-closed 处理为证据无效并阻止名单锁定。
- 旧活动证据模式为空时，基础预览可以运行，但名单锁定和外部动作全部关闭。

## 10. 模式变更

- `发起新分析 → 不使用`：允许；必须填写变更说明，清空竞品品牌、帖子与事件，状态改为不适用，然后生成新的基础排序版本。
- `引用历史证据 → 另一证据`：旧排名快照保留，未发送候选重新排序并再次锁定。
- 发生真实发信后变更模式属于未来阶段；只影响尚未发送对象，已发送参与记录保留原排序快照历史。
- 任何模式变化都不得删除历史参与记录，也不得改写已发生的邮件或结果数据。

每次模式变更必须携带 `expected_config_version`；版本不一致返回冲突，操作者需刷新后重试。飞书记录历史提供字段级审计；活动字段中的版本、快照时间和变更说明提供运营可直接查看的业务留痕。本期不另建决策日志表。

参与记录每次锁定或重新确认都向 `排序快照历史` 追加一条不可变 JSON；旧条目不覆盖。每条快照至少保存：

- `ranking_version`、基础分、最终优先级、证据等级、排序组和时间；
- 身份匹配路径及当时使用的稳定身份键；
- 每条证据当时的帖子 ID、平台、内容类型、发布时间、表现指标字段、表现值；
- 长期合作首帖日期、末帖日期、跨度天数；
- P75 分组键、样本数、阈值、候选命中值和是否达到阈值；
- 基础筛选结论与全局重复触达决策。

因此竞品帖子后续修改或删除后，单条回放仍能解释当时的 A/B/C 判断。最多保留 10 个版本，超过上限时阻止继续变更并要求人工归档，不静默删除历史。

## 11. 戴夫试点的 NYXI 排序

### 11.1 作用范围

同时满足以下条件才启用：

- 当前 `campaign_id=launch-20260915-funlab-dave-ys11-5`，活动 record_id=`recvsFoRmeGj4Y`；
- 产品主记录 record_id=`recvkJOoCsNb1s`，活动归并键=`launch-20260915-funlab-dave-ys11-5`；
- `竞品证据模式=引用历史证据`；
- `竞品品牌=NYXI`；
- 至少一条关联 NYXI 帖子已经人工确认；关联营销事件仅作可选背景；
- 候选对象为 KOL。

不符合其中任一条件时，竞品证据不参与排序。

### 11.2 身份匹配

按以下顺序匹配竞品帖子作者与 KOL 主表：

1. 竞品帖子已经存在 `关联KOL`；
2. `平台 + creator_id` 完全一致；
3. 规范化主页 URL 完全一致；
4. `平台 + 规范化 Handle` 完全一致；
5. 仍无法确认时标记 `待人工匹配`，不自动加分、不自动新建联系人。

不得仅按展示名、模糊字符串或邮箱猜测身份。

### 11.3 证据等级

只使用 `人工复核状态=已确认`、`相关性=相关` 且合作信号为 `明确合作` 的帖子。不同平台和内容类型分别比较表现，不把 YouTube 与 X、Shorts 与长视频直接混排。

表现指标统一取帖子 `曝光量`；为空时可降级到 `覆盖量`，两者都为空时不参与高表现判断。按 `平台 + 内容类型` 分组，在活动直接关联的帖子证据快照内计算 P75：

- 分组最少需要 8 条已确认样本；不足 8 条时该组不授予“前25%”资格。
- P75 使用 nearest-rank：排序后取 `ceil(0.75 × n)` 位的值。
- 指标大于或等于 P75 即合格；并列值全部合格。
- 长期合作定义为同一作者至少 2 条明确合作帖子，首末发布时间相差不少于 90 天。

| 等级 | 条件 | 排序处理 |
|---|---|---|
| A | 明确合作帖子不少于 2 条、首末跨度不少于 90 天，且至少一条表现位于同平台已确认样本前 25% | 新开发池第一优先组 |
| B | 满足“长期合作”或“同平台前 25% 表现”其中一项 | 新开发池第二优先组 |
| C | 有一次明确合作，但不满足 A/B | 基础评分固定增加 5 分，不独立置顶 |
| 无加分 | 自然提及、疑似寄样、无关、待复核或证据不足 | 使用基础评分 |
| 待人工匹配 | 证据有效但作者身份不能稳定对应 KOL | 不加分，进入人工匹配视图 |

### 11.4 排序顺序

1. 先执行国家、语言、平台、内容风格、粉丝量级和硬性排除检查。
2. 先执行全局重复触达预检，分为同线程激活、新开发、暂缓和排除。
3. 同线程正向关系保留为独立暖关系池。
4. 新开发池内部排序：A 组 → B 组 → 其他候选；C 级只在其他候选内部获得小幅优势。
5. 同一证据等级内按现有基础评分降序排列。

最终优先级数值用于稳定排序：A=`3000+基础分`，B=`2000+基础分`，C=`基础分+5`，无加分=`基础分`。暖关系池与新开发池分开展示，不用该数值跨池比较。完全同分时直接按联系人 record_id 升序，不再比较跨平台原始曝光。

## 12. 只读接口

### 12.1 活动候选预览

扩展现有 `POST /launch/candidates/preview`：

- 新增必填 `campaign_id`；
- 产品从活动记录读取并核对，不能仅凭外部传入的产品 ID 绕过活动范围；
- 返回 `evidence_mode`、`evidence_status`、`evidence_pending`、`ranking_version`；
- 每位候选返回基础分、证据等级、使用的帖子 ID、排序分组和人话理由；
- 始终返回 `read_only=true`、`writes=0`。

### 12.2 单条回放

扩展现有 `GET /launch/candidates/replay`：

- 新增 `campaign_id`；
- 返回身份匹配路径、证据帖子、证据等级、基础过滤、重复触达决策和最终排序原因；
- 能按保存的排序版本重放已锁定参与记录。

### 12.3 证据配置接口

`POST /launch/campaigns/evidence/configure`

请求字段：`campaign_id`、`mode`、`competitor_brand`、`post_record_ids`、`event_record_ids`、`change_reason`、`expected_config_version`。服务按第 9.4 节验证合法组合并递增版本。认证复用现有 KOL 服务内部 Bearer token。

该接口按活动 ID 获取互斥锁，先完成全部回读和校验，再以一次活动记录更新写入完整目标配置：

- `发起新分析`：要求品牌必填、帖子和事件为空；先创建或复用研究节点，然后原子写入 `模式=发起新分析 / 状态=待分析 / 品牌 / 空帖子 / 空事件 / 新配置版本`。若活动更新失败，旧配置和版本保持不变，研究节点标记为阻塞且外部动作关闭。
- `引用历史证据`：要求品牌必填、至少一条已确认且相关的同品牌帖子；事件可空，填写时必须已确认。全部验证通过后原子写入 `模式=引用历史证据 / 状态=已就绪 / 品牌 / 帖子 / 事件 / 快照时间 / 新排序版本 / 新配置版本`。
- `不使用竞品证据`：原子写入 `模式=不使用竞品证据 / 状态=不适用 / 空品牌 / 空帖子 / 空事件 / 新基础排序版本 / 新配置版本`。

任何预校验或活动写入失败都不递增版本、不部分覆盖字段，并保留旧配置。只有活动记录完整写入成功后才返回新配置版本。

`start/submit/confirm/retry` 接口使用相同鉴权和版本校验。每个请求都必须携带 `expected_config_version`；每次成功状态转换把活动 `证据配置版本` 恰好增加 1：

- `start`：`待分析 → 分析中`；
- `submit`：把候选集合保存到节点，`分析中 → 待人工确认`；
- `confirm`：只接受当前节点候选集合的子集，`待人工确认 → 已就绪`并生成新排序版本；
- `retry`：`失败 → 待分析`，旧节点候选因提交版本不等于活动新版本而失效。

跨活动记录和节点的写入以活动版本为提交标志。辅助节点先写目标版本，活动记录最后更新；活动更新失败时旧配置和旧版本保持不变，节点标记为阻塞且其目标版本不生效。只有活动记录写入成功才返回成功和新版本。

版本冲突返回 HTTP 409；字段组合或非法状态转换返回 HTTP 422；活动、帖子或事件不存在返回 HTTP 404。

### 12.4 名单锁定与参与记录写入

`POST /launch/participants/lock`

请求字段：`campaign_id`、`product_family_id`、`object_type`、`contact_ids`、`expected_ranking_version`、`lock_batch_id`，失败恢复时另带 `recovery_of_batch_id`。`contact_ids` 是该活动、产品和对象类型在当前排序版本下的**完整替换名单**，不是增量追加；单批最多 100 人。

处理顺序：

1. 获取活动级互斥锁并回读活动、证据配置版本、排序版本和产品主记录。
2. 要求请求的 `product_family_id` 等于活动 `产品主记录ID`；不一致返回 HTTP 422，禁止调用方替换产品范围。
3. 服务重新生成同一活动的完整候选预览，并对每位提交对象重新执行国家、语言、平台、内容风格、粉丝量级、硬性排除、身份唯一性和全局重复触达检查。只有当前预览中的 `eligible_new_cold` 或 `reactivation_same_thread` 可锁定；调用方不能通过直接提交 contact_id 绕过资格。
4. 预期排序版本不一致时返回 HTTP 409，不写任何记录。
5. 先完整预校验所有候选；任一硬错误则整批拒绝。
6. 以活动当前 `已锁定名单版本` 为旧版本，计算三组：本次继续保留、本次新增/恢复、旧版本中本次被省略。服务保存每条被修改记录的旧状态和旧名单版本，作为本批回滚依据。
7. 在活动互斥锁和外部动作关闭状态下，串行准备完整新名单：新记录和本次恢复记录写为 `已入围`、`名单版本=expected_ranking_version`、新批次 ID；继续保留的历史 `已入围` 更新到同一名单版本。历史 `已取消` 只有 `取消原因代码=锁定失败` 时可恢复，`运营取消/不再符合` 本期拒绝。此时活动的 `已锁定名单版本` 尚未改变，因此准备中的新版本不会被读取为当前名单。
8. 全部目标记录写入并回读成功后，以更新活动 `已锁定名单版本=expected_ranking_version` 作为唯一提交点。当前名单只认同时满足“`名单版本=活动已锁定名单版本`”和“状态属于当前可执行状态”的记录；因此提交后，新版本立即成为唯一当前名单，旧版本记录即使尚未清理也不会继续生效。
9. 提交后，把旧版本里未被本次完整名单选中的、仍处于外联前状态的记录改为 `已取消/不再符合`。若未来存在已经发送、回复、寄样或上稿的记录，不自动取消，只保留为不可逆历史；本期不会产生这些状态。
10. 若提交点之前任一步失败，按本批保存的旧值回滚所有已改记录，并把本批新建记录改为 `已取消/锁定失败`。回滚完整成功时，活动写 `活动阻塞代码=LOCK_BATCH_RETRYABLE`、`阻塞待处理记录` 为空；旧名单版本继续有效。恢复请求必须带与失败批次一致的 `recovery_of_batch_id`，可在活动阻塞期间重试当前或更新后的排序版本；只有整批成功后才清空阻塞代码。
11. 若回滚、取消或提交后清理旧记录任一项失败，活动写 `活动阻塞代码=LOCK_BATCH_MANUAL_REVIEW` 并把 record_id 写入 `阻塞待处理记录`；禁止自动重试和一切外部动作，必须人工修复后显式解除阻塞。若唯一键查出重复记录，则使用 `DUPLICATE_PARTICIPANT_MANUAL`，处理规则相同。
12. 本接口不支持“运营手工加入”绕过基础资格；该能力如需开放，另行设计带理由和权限的人工覆盖接口。
13. 本接口不创建 KOL/媒体人任务、邮件草稿、卡片、寄样或邮件。

响应返回 `lock_batch_id`、活动/排序版本、创建数、复用数、取消数和每位对象的参与记录 ID。鉴权复用现有内部 Bearer token。

## 13. 外部动作门槛

名单锁定必须同时满足：

- 活动运行模式允许：活动无阻塞，或仅处于 `LOCK_BATCH_RETRYABLE` 且本次请求带匹配的 `recovery_of_batch_id`；`LOCK_BATCH_MANUAL_REVIEW` 和 `DUPLICATE_PARTICIPANT_MANUAL` 一律拒绝自动执行；
- 竞品证据模式已选择；
- 若为新分析或历史引用，证据状态为 `已就绪`；
- 候选预览成功，且没有身份匹配或重复触达硬错误；
- `名单锁定授权=true`。

### 13.1 本期硬边界

本期所有外部动作开关保持关闭。参与记录接口只能写到 `已入围/已取消`，不得写 `已批准触达` 及后续状态；不得创建任务、草稿或触发发送。以下真实发信条款仅是未来阶段接口契约，不在本期实现。

### 13.2 未来阶段接口契约

未来真实发信还必须满足现有全部邮件安全闸，并额外满足：

- 参与记录状态为 `已批准触达`；
- 关联任务/草稿属于同一 `campaign_id`；
- `发送邮件授权=true`；
- 账号级限额允许；
- 首封真实开发信需有独立放行记录，至少包含 `campaign_id`、`lock_batch_id`、批准人、批准时间、有效期和一次性 nonce；发送器成功使用后标记已消费，不能跨活动、跨批次或重复使用。该记录的数据落点和接口在真实外联阶段另行设计。

## 14. 异常处理

| 情况 | 处理 |
|---|---|
| 新竞品分析失败 | 活动准备继续；锁名单和发信保持关闭；运营选择重试、历史证据或不使用 |
| 历史证据被驳回或删除 | 不再用于新排序；已锁定记录保留快照；未发送候选需重新排序 |
| 作者匹配到多位联系人 | 标记待人工匹配，不加分、不发信 |
| 同一参与记录重复创建 | 依唯一键返回原记录，不新增重复行 |
| 活动模式被切换 | 生成新排序版本；下次锁定请求提交完整替换名单，旧版本未发送且被省略的候选退出当前名单 |
| 证据等待期间误勾发送授权 | 发送层仍因名单锁定门槛失败而拒绝 |
| 活动参与表写入失败 | 不创建任务或草稿；返回可回放错误，不允许部分放行 |
| 活动证据变化与名单锁定并发 | 以配置版本和排序版本校验拦截；版本变化返回409并整批不写 |
| 批量锁定部分写入失败，且回滚完整 | 旧名单版本继续有效；活动标记 `LOCK_BATCH_RETRYABLE`；只接受携带原失败批次 ID 的恢复请求 |
| 回滚、取消或旧名单清理失败 | 活动标记 `LOCK_BATCH_MANUAL_REVIEW` 并保存待处理 record_id；人工修复和显式解锁前禁止自动重试 |
| 唯一键实际存在多行 | 活动标记 `DUPLICATE_PARTICIPANT_MANUAL`；不猜测保留哪一行，转人工修复 |
| 已取消记录再次锁定 | 仅`锁定失败`可由新批次自动重试；`运营取消/不再符合`本期拒绝自动恢复 |

## 15. 容量与性能

- 候选基础预览不把全部候选写入飞书。
- 只有通过资格检查并入围或同线程激活的对象建立参与记录；本期不支持手工绕过。
- 竞品帖子通过关联字段引用，不复制完整正文和整套互动/曝光字段；`排序快照历史`只保存重放决策必需的精简指标值。
- 候选预览一次加载所需表并建立内存索引，避免每位候选重复全表查询。
- 证据排序只读取活动的 `关联竞品帖子`，不从营销事件扩展帖子，也不扫描该竞品品牌的其他帖子。

## 16. 验收与测试接口

已确认的测试边界覆盖全部活动证据和名单接口：

1. **证据配置 `configure`**：验证三种模式的原子目标状态、字段清空规则和配置版本。
2. **新分析状态组 `start/submit/confirm/retry`**：验证合法转换、非法转换、节点候选持久化、确认子集和版本推进。
3. **候选预览**：验证三种模式的门槛、戴夫 NYXI 排序和非戴夫活动隔离。
4. **单条回放**：验证同一个候选能说明身份匹配、证据等级、重复触达和当前/历史排序原因。
5. **名单锁定 `participants/lock`**：验证活动产品绑定、完整资格重算、完整替换语义、唯一键防重复、并发冲突、历史复用、版本提交点和批量失败恢复。

关键验收场景：

- 戴夫活动引用 NYXI 后，已确认的 A/B 级作者在新开发池优先；基础硬门槛不合格者仍被排除。
- 同一 KOL 在食人花活动和日常预览中不获得 NYXI 优先级。
- 选择“不使用竞品证据”时不等待证据，也不改变基础评分。
- 选择“发起新分析”且证据未就绪时，预览成功但锁名单与发信均被拒绝。
- `configure` 对三种模式分别写出矩阵规定的完整字段组合；任一活动写入失败都保留旧配置且版本不增加。
- `start/submit/confirm/retry` 每次成功只增加一个配置版本；非法转换返回422，旧版本请求返回409，不存在的活动/帖子/事件返回404。
- `submit` 后换页面或换审核人仍能从活动节点读取候选；`confirm` 不能选择当前提交集合之外的帖子。
- 证据模式变更后生成新排序版本；已发送参与记录保持原版本。
- 第二次锁定省略旧名单中的未发送候选后，该候选被改为`已取消/不再符合`；活动 `已锁定名单版本` 对应的新版本是唯一当前名单。
- 对相同活动和联系人重复创建参与记录不增加行数。
- 锁名单携带旧排序版本时返回409并且写入0行。
