# KOL集中宣发任务日报卡设计规格

日期：2026-08-21  
状态：已由 Frankie 确认进入开发

## 1. 目标

每天用一张只读飞书卡片汇总全部正在执行的集中宣发活动，让 KOL 运营无需打开多张表即可判断：今天新增了多少合格候选、发了多少活动开发信、累计进展如何、邮箱额度是否在合理使用、系统下一步会做什么。

这项自动化替代的是运营每天重复翻表、跨活动计算和判断是否需要补池的动作。Frankie 只审规则和异常，不逐条审名单。

## 2. 本次范围

- 卡片标题固定为 `KOL集中宣发任务日报 · YYYY-MM-DD`，不加旧式 `[KOL·P2]` 前缀。
- 使用飞书 Card JSON 2.0 原生组件：彩色状态标签、彩色头部和紧凑文本进度条。禁止使用 `chart/linearProgress`：飞书桌面端会按全宽比例把每条图表撑到接近一屏高。
- Card JSON 2.0 正文说明统一使用`markdown`；禁止旧版`note`组件（飞书会以`200861 unsupported tag note`在创建消息前拒绝整张卡）。
- 第一张真实样卡仅发 Frankie，不发运营群；用户确认实际渲染后才启用每天 17:15（北京时间）的群定时发送。
- 自动纳入 `运行模式=正式运行` 且 `状态=正式执行中` 的集中宣发活动；活动离开该状态后从次日日报退出。首版生产回放必须至少命中当前两项活动：
  - `launch-20260915-funlab-dave-ys11-5`
  - `launch-20260915-powkong-piranha-v2`
- 食人花发信修复验证只由 Codex 做只读检查，不发飞书卡片。
- 本卡不补池、不建草稿、不发邮件、不修改活动统计或参与记录。`notify=false`完全只读；显式发卡时，只允许在一个活动的`数据口径备注`写“发送中/已发送”技术回执，用于跨服务重启防重复，并单独汇报技术写入次数。

## 3. 统计口径

所有“活动开发信”只统计活动参与记录关联的唯一草稿 ID，且 `邮件草稿来源=cold`、草稿发送状态为真实已发送；同一草稿被脏重复关联时只计一次，跟进、寄样、报价等邮件不得计入。

| 指标 | 口径 |
|---|---|
| 今日合适入池 | 参与记录当前为有效参与状态、审核结论为通过；人工审核以审核时间为准，系统建议通过以记录创建时间为准；两者均缺失时不猜测并另显示缺失数 |
| 当前合适入池 | 当前有效参与状态且审核结论为通过的参与记录 |
| 当前可发送池 | 当前活动已审核通过、未发送且已到发送时间的草稿库存 |
| 今日活动开发信 | 活动参与记录关联草稿在北京时间当天真实发送成功 |
| 累计活动开发信 | 活动参与记录关联草稿累计真实发送成功 |
| 今日回复 / 累计回复 | 只统计活动关联草稿；今日以回复日期落在北京时间当天为准 |
| 明确承诺上稿 | 活动参与记录已有可验证承诺上稿时间 |
| 按时上稿 / 目标 | 活动参与记录的实际上稿时间不晚于窗口结束 / 活动目标上稿数 |
| 全部已上稿 | 活动参与记录已有实际上稿时间；仅作补充事实，不用于填满主进度 |
| 品牌邮箱额度 | Zoho 发件箱滚动 24 小时全部外发 / 当前品牌硬上限；不等同活动开发信 |

“今日合适入池”优先使用现有业务字段“审核时间”；仅当 `系统审核分流=系统建议通过` 时，允许使用飞书 `automatic_fields=true` 返回的记录创建时间，因为系统通过与建记录是同一动作。不得用记录更新时间或当前时间猜测；仍缺时间的记录单独显示为数据缺口，不计入今日数。

## 4. 卡片内容

顶部总览：执行中任务数、今日合适入池、今日活动开发信、按时上稿/总目标。

每项活动显示：品牌和活动名、状态标签、今日合适入池、当前合适入池、当前可发送池、今日/累计活动开发信、今日/累计回复、明确承诺、按时上稿/目标、全部已上稿、品牌邮箱滚动 24 小时额度、两行紧凑进度信息、系统下一步。

底部固定说明：

> 活动开发信只计算“活动参与记录”关联且真实发送成功的开发信；邮箱额度按 Zoho 滚动24小时全部外发邮件统计，两者口径不同。

## 5. 状态规则

- 规则优先级固定为红 > 绿 > 橙 > 黄，先命中的最高优先级生效。
- 红色“数据异常”：Zoho 权威计数失败、活动ID/品牌/目标/窗口结束等关键数据缺失、统计过程失败，或滚动24小时发送数超过硬上限。
- 绿色“进度正常”：按时上稿已达到目标；或当前到期可发送池 `>= min(12, 邮箱剩余额度)` 且没有红色异常。
- 橙色“进度落后”：按时上稿未达到目标、邮箱剩余额度 `>= 12`，且当前到期可发送池为 `0`。
- 黄色“需要关注”：没有命中红/绿/橙；包括库存小于绿色阈值、系统正在补池或存在待审核对象。
- 上稿和额度进度统一计算为 `已完成/目标`，分母小于1时视为红色数据异常；显示百分比截断到 0–100，超额事实仍在文本中显示实际数。

状态必须附一条普通中文的“系统下一步”，不能只给颜色。

## 6. 飞书安全与发布闸

- 使用现有 KOL 通知 App（聪哥分身1号）发送。
- 样卡收件人固定为 Frankie 在该 App namespace 的 open_id。
- 端点默认 `notify=false`、`frankie_only=true`；只有显式 `notify=true` 才允许发送。
- 群发还必须同时满足独立环境开关 `KOL_LAUNCH_DAILY_GROUP_ENABLED=1`，且目标 chat_id 精确等于当前 `NOTIFY_CHAT_ID=oc_8b71a652a25ec0dd1c8af2c53e86ed93`；否则拒绝，不降级到旧群或个人列表。
- 卡片没有按钮、表单或回调，避免误操作。
- 全池统计走“后台计算 + 任务状态查询”，请求先立即返回 `job_id`；同一天、同收件对象、同活动集合只允许生成一份发送回执，网关重试或重复点击复用原任务/原消息，不重复发卡。后台请求先把空日期解析成北京时间实际日期，并读取当前执行中活动ID集合；活动集合变化时必须重新计算。
- 防重采用两层：飞书发送请求使用确定性 `uuid` 拦住并发和短时重试；发送前后把同一键的技术回执写入活动`数据口径备注`并回读，覆盖Zeabur重启和当日延迟重试。业务字段保持只读。
- 若重启后只找到`发送中`回执，系统不得猜测“没发出去”并自动重发，必须暂停并提示按`uuid`核查；技术回执空间不足时硬失败，禁止截断任何既有业务备注。
- 只有飞书明确返回HTTP 400且`Failed to create card content`（消息创建前的结构拒绝）时，才能把回执改为`rejected`并允许修正结构后重试；超时、空message_id等不确定失败继续停在`发送中`，不得自动重发。
- 技术回执只保留当前日报日期的键；写新日期时自动清理旧日/损坏的技术回执，但逐字保留全部非技术业务备注，防止回执按天累积挤满字段。
- 同一封邮件草稿若同时关联两个执行中活动，不能任意归属或重复计数：从两个活动的活动开发信/回复统计中同时排除，并把两个活动标为红色“数据异常”，提示运营修复关联关系。
- 结构自检必须通过：根对象 `schema=2.0` 且存在 `header/body.elements`、标题正确、每个执行中活动均存在、每活动一块紧凑进度信息、完全不含 `chart` 画布、不强制全宽显示、状态颜色合法、必需指标齐全、无 form/button、JSON 小于 30KB。没有执行中活动时返回空态卡，不伪造活动或进度信息。
- 样卡发送后保存实际 payload、校验结果、API message_id；能回读时再核对发出的 content。
- 样卡未获 Frankie 确认前，不新建或启用群定时任务。
- 当天没有执行中活动时仍返回合格空态卡JSON，但不主动发送一张无任务卡片，结果明确标记`empty_state_send_skipped=true`。

## 7. 公开测试入口

1. `launch_daily_report.run(...)`：使用固定活动/参与记录/草稿/额度样本，验证统计口径、状态、Card JSON 2.0、自检及只读输出。
2. `feishu.send_card_message(..., format_title=False)`：验证日报标题保持原样；默认 `format_title=True` 继续保留现有通知标题规则，避免影响其他生产卡片。
3. 部署后用真实生产数据执行 `notify=false` 回放，并通过调用替身断言不会调用事实回填、补池、建草稿、更新记录、Zoho邮件发送或飞书IM发送。

## 8. 验收标准

- 聚焦测试通过，且现有相关测试无回归。
- `notify=false` 可返回完整卡片和统计，不发送飞书消息，也不做任何业务写入。
- `frankie_only=true` 只调用一次 Frankie 私聊发送，不触达运营群。
- 实际样卡 title 精确为 `KOL集中宣发任务日报 · 2026-08-21`，能看到彩色状态标签与每活动两行紧凑进度信息；整张卡在飞书桌面端首屏内能看完两个活动，不出现整屏留白。
- 样卡 message_id 和 payload 校验结果可追踪。
- 群定时发送仍保持未启用，等待用户确认样卡。
